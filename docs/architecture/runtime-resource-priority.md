# Web 响应、执行控制与后台任务的资源优先级

资源冲突时，优先维持 Web 响应，其次保障执行控制与日志上传，统计刷新、导入导出和保留清理使用剩余资源。这是应用层的隔离、限流和退让策略，不是操作系统实时调度保证。

## 独占主机与容器资源利用

线程数量不再固定为 Lite 最多 4 条、Full 最多 2 条。启动时结合 CPU affinity、cgroup v1/v2 的当前组及祖先 CPU quota、宿主机内存和进程内存限制计算资源计划；Docker `--cpus=1.5` 不会被误认为可使用整台宿主机的 CPU。资源计划写入启动诊断日志，调整容器配额后需重启平台。

Web、执行控制、日志与快照共用一份线程预算，不让每个线程池独立申请整台主机的 CPU。除必要的隔离线程外，每枚空闲 CPU 最多增加两条可交替等待 I/O 的线程，并受内存预算约束；这不是绑核或实时调度。Lite 的不同执行尝试可并行压缩日志，Full 的日志写入按 attempt ID 分配线程，同一尝试的追加与水位写入保持顺序。日志读取选择待处理请求较少的线程，后台快照也可以通过独立构建租约并行处理不同查询。

工作线程的 V8 old-space 总预算按可用内存约 40% 分配，每线程 128–4096 MiB，其余容量留给 Web、原生 Buffer、SQLite 页缓存、其他容器与系统；最低隔离线程在小内存机器上可能超过该比例。堆上限不是预分配内存，也不是 RSS 硬限制。不要为了占满内存而分配无用缓存，主线程堆继续采用 Node 的容器感知默认值；不要用全局 `--max-old-space-size` 覆盖全部线程的独立堆限制。

Compose 的 Web 与 worker 默认不设置 CPU/内存硬上限；`cpu_shares` 分别为 2048 和 1024，在竞争时提高 Web 的相对权重，空闲资源仍可被 worker 使用。可在部署 `.env` 中设置 `AUTOFORGE_WEB_CPUS`、`AUTOFORGE_WEB_MEMORY_LIMIT`、`AUTOFORGE_WORKER_CPUS`、`AUTOFORGE_WORKER_MEMORY_LIMIT`，默认 `0` 表示不额外限制。独占平台主机可使用默认值，同机部署数据库或 Runner 时应按实测 RSS 与数据库缓存划分内存，避免多个进程分别按整机容量计算预算。

SQLite 单文件写事务仍需串行；同一批次的权威状态迁移也有必要的并发保护。多线程用于独立 CPU 工作和 I/O，并不会让这些数据库约束消失。是否继续扩大资源应以吞吐、页面延迟、锁等待和 RSS 实测为准；CPU 没有达到 100% 本身不代表浪费。

资源检测与部署语义参考 [Node OS API](https://nodejs.org/api/os.html)、[Node process memory API](https://nodejs.org/api/process.html)、[Worker 资源限制](https://nodejs.org/api/worker_threads.html) 和 [Docker 资源约束](https://docs.docker.com/engine/containers/resource_constraints/)。

## 日志读取与上传

Lite 和 Full 的日志正文仍保存在所属节点的批次 SQLite 文件中。Web 本地日志 I/O 使用独立的读取、写入和文件维护线程；Full 的跨节点请求到达所属节点后也走这些线程。Lite 的上传、完成水位与 reconcile 在执行控制工作线程完成，读取另走日志线程。

- 查询只读打开文件，不创建缺失文件，不建索引、不补列。旧库的 `identity` 正文可以直接读取；首次追加才补齐压缩元数据列，新增列不使用会扫描历史行的 `CHECK`。新文件仍包含格式约束。
- 新批次文件已出现但日志表尚未初始化时，读取返回空日志且不缓存该连接；首次上传完成后下一次查询重新打开并读取正文，避免立即点击重跑日志时出现 `no such table`。实际损坏、异常 schema 或磁盘错误仍正常报告，不当作等待日志处理。
- LRU 淘汰与关闭不再主动执行 `wal_checkpoint(TRUNCATE)`。自动检查点由 SQLite 写连接负责。其他线程删除文件后，缓存连接在下一次访问时失效，不能继续读取已删除的正文。
- 单次返回以 1 MiB 正文为预算，至少保留一个完整块，按最多 32 行的小批次解压。游标仍是最后返回的序号。关键字搜索最多扫描 4,096 块，超出时提示缩小时间范围；时间条件导致的慢 SQL 由线程超时兜底。公开页仍只展示有界预览。
- 每条读取通道最多接纳 16 个请求，包含排队时间在内的期限为 5 秒。超时中止读取线程并拒绝待处理请求，旧线程退出后才允许重建。读取超时不会终止写事务。
- Full 每条本地写入通道最多 64 个请求、16 MiB 排队正文，调用期限为 15 秒。超时后在途写操作保留执行槽直到返回；结果可能已经提交，Runner 按原协议幂等重试。Lite 每个日志上传车道也同时限制 64 个请求与 16 MiB 正文，允许小日志突发而不会让大载荷无限排队。文件维护通道最多 4 个请求、5 秒期限。
- 日志线程中的同步 codec 避免占用 Web 的 libuv 文件/DNS 队列。解压受已记录的正文大小约束。
- 同一 Web 节点同时接受最多 `8 × 日志读取线程数` 个公开日志页面或日志查询 API 请求。超限返回 `503` 和 `Retry-After: 2`；API 返回稳定错误码和 request ID。页面导航或 Runner 上传不占用这一配额。

日志错误、超时或拥塞时，失败请求可重试，公开日志页有重试入口。线程队列不承担持久化职责。未确认日志继续由 Runner 本地 spool 重传；原有租约、日志配额和上传期限仍然有效，不能通过忽略租约失效来维持表面上的运行。

## 执行与后台工作

Lite 的批次创建、补位调度、定时批次创建、日志上传、租约/领取/完成/reconcile 和后台维护使用不同工作线程。Full 独立 Worker 也把 JAR/DDT 导入、对象清理、分析导出以及周期通知、保留清理放入工作线程，避免异步函数中的同步解析占住调度事件循环。上传 HTTP 请求中的 JAR 检查、来源解析和 DDT 列名预览同样在线程中完成；每条解析通道最多接纳两个请求，过载返回可重试错误，重复列的原有交互保留。

执行派发和后台任务分别领取持久队列，后台暂停发生在领取之前，不消耗执行派发的并发槽或预先租住任务。SQLite 按工作类型使用独立部分索引，避免十万条导入积压导致派发扫描和排序全部队列。Full 为后台消息使用独立的 JetStream subject 和 durable consumer；原有 ready subject 中的旧后台消息在新 subject 发布确认后才确认旧消息，保留重投递与去重语义。

Full 独立 Worker 的后台线程总预算为 CPU 整数容量与约 40% 内存 / 256 MiB 的较小值，至少两条隔离线程。其中约四分之一用于快照，其余维护线程同时受配置并发和数据库连接数限制。4 CPU、4 GiB、配置并发至少 3 时使用 3 条维护线程和 1 条快照线程；Web 的维护线程单独预算，不再与 Full 补位调度复用。一个不可拆分的任务不会为占满 CPU 而复制执行，独立任务和不同查询可并行。取消信号跨线程传递，业务结果仍由原有应用用例持久化。

Web 每 250 ms 检查事件循环延迟。出现至少 100 ms 的延迟时，后台工作退让至少 5 秒；执行控制在途操作达到资源计划中的容量阈值时也暂缓新的后台工作；少量在途请求不会让其余 CPU 空闲。同时监测整个 Web 进程的 CPU 时间和可用内存，达到容器 CPU 容量的 85% 或可用内存低于 15% 时触发退让。判断使用单调时钟，宿主机校时不会延长退让窗口。**不能仅因 HTTP 请求未结束就暂停后台**：页面可能正在等待首次快照，这种等待不能阻止后台生成快照。

快照工作器在领取、写分片和发布前检查资源预算。退让时保留已经发布的快照，释放构建租约并在 1 秒后允许重试，不累计失败次数；部分新分片不能成为可见代次。正在运行的 SQL 不由这一标志强制打断。持续执行压力下统计可以暂时滞后，缓存不能参与执行资格、权限、租约或删除判断。目录页面收到新快照时只更新目录投影，同一代次只触发一次更新，避免后台刷新反复重载整页、打断 TestNG/DDT 切换和搜索；用户显式点击刷新时仍更新整页任务元数据。

首次访问且还没有任何已发布快照的查询属于页面等待路径。每个 Web 节点最多保留一条线程，在执行拥塞或普通 CPU 退让期间继续领取这类查询；不会因此刷新已经有缓存的统计。初始快照仍受构建租约、修订号和 SQL 限制保护，可用内存不足时同样暂停。这样无需等待整批执行结束才生成第一次页面数据。

SQLite Web 与后台统计/维护连接使用 25 ms 锁等待。页面快照的首次注册或访问续期允许最多 9 次异步短锁重试（默认退避与等待合计约 2.5 秒），避免原子导入事务让冷查询立即失败；正常写操作仍使用原有 6 次预算。快照构建遇到 SQLite 锁竞争或 PostgreSQL 锁等待、死锁、序列化冲突时，释放构建租约并延后重试，不累计永久失败次数；SQL 超时、损坏和约束错误仍走正常失败路径并通知。后台统计事实按 100 项补齐，避免 Web 定时承担补算。执行批次创建、JAR/分析导出入队与状态推进、DDT 预览/确认/落库与进度更新、服务账号条件更新和独立审计写入在短锁竞争时异步退避重试整个原子写入，避免后台导入让正常新请求立即失败。重试有界；持续锁竞争仍映射为可重试 `503`，不会在 Web 事件循环中等待默认的 5 秒；工作线程业务事务保留原有恢复规则。

Lite/Full 的会话鉴权均为只读查询，继续实时校验用户状态、权限、过期与撤销，不为每个 GET 更新会话记录，避免页面轮询与导入、调度争抢写锁。登录和已有的前台会话续期流程更新 `lastSeenAt`；浏览器续期间隔为 5 分钟，因此会话列表中的活动时间按续期粒度显示，不表示每次资源请求的时间。

SQLite 调度与执行控制事务同样采用有界异步锁重试：分配、调度事件、轮次并发、领取、续租、完成、产物状态、恢复与取消从完整事务入口重试，日志正文成功追加后单独重试主库路径登记。这样短时写锁竞争不会立即变成 Runner 的领取失败，同时保留幂等回执、真实版本冲突和租约校验。持续竞争超过重试预算仍返回可重试错误，不延长既有租约。

Runner 心跳写入也使用同一套最多 6 次的 SQLite 异步锁重试，保留 Web 连接的 25 ms 单次锁等待，不通过延长同步等待阻塞页面。短锁释放后，同一请求可以继续更新原 Runner 的活性与资源指标，无需重装或更换凭据；超过预算仍返回可重试错误，后续心跳可以恢复。心跳不续租，也不代替执行完成上报。

SQLite 快照领取先只读检查是否有到期候选，没有任务时不申请写锁；实际领取仍由带完整条件的原子 UPDATE 决定，多个线程不能重复取得同一租约。统计事实没有新增记录时直接返回，不开启空写事务。Lite / Full 的事实补齐仍每批最多 100 项；空闲或失败时使用单调时钟将轮询间隔从 1 秒逐步退避到最多 30 秒，发现新增事实后恢复 1 秒补齐。长时间空闲后的新增统计因此最多额外等待一次 30 秒轮询，之后还受既有快照刷新周期影响；首次页面快照仍独立领取，事实扫描失败不会跳过本轮页面构建。

Full 调度预留 Runner 容量时使用 `FOR NO KEY UPDATE` 行锁，多个调度者仍串行重新核算容量，但领取租约插入时的 Runner 外键校验可以持有 `KEY SHARE` 锁。调度不修改 Runner 主键，因此不需要阻止这些外键引用，避免形成“调度持有批次等 Runner、领取持有 Runner 引用等批次”的死锁。

Full Web 的执行控制使用独立连接池，上限为 `min(databasePoolMax, max(4, ceil(CPU容量 / 2)))`，避免等待日志 I/O 的完成事务占满页面连接；页面主池保留原配置上限。每条 Web 快照/维护线程，以及独立 Full Worker 的每条快照/维护线程，各使用独立的 1 连接池，与调度和 outbox 分开。快照 PostgreSQL 语句期限为 2 秒、锁等待为 50 ms；业务导入事务沿用业务限额。每个使用平台时钟的数据库句柄另外使用一条专属校时连接，连接与查询期限均为 2 秒，避免业务池全部被事务占用时停止采样。独立 Worker 在调度达到容量阈值、内存不足或事件循环过载时暂缓后台刷新；主业务池出现排队时也暂停领取新的维护作业。多节点仍共享 PostgreSQL 的 CPU、锁与存储资源，容量规划需计入这些额外连接。连接预热即使部分失败，也会归还所有已经借出的连接，避免后续请求和关闭流程永久等待；双节点验收采用与五主机部署模板一致的 `max_connections=200`。

## 通知与部署

日志异常、执行控制线程异常、Web 延迟、CPU/内存压力、数据库锁竞争、后台刷新和周期维护失败通过现有通知功能反馈给活跃且拥有系统级 `settings.manage` 权限的用户。原始 SQL、凭据和日志正文不进入通知。

资源保护与告警分别判断：单次 CPU / 内存或事件循环尖峰立即触发原有 5 秒后台退让；只有压力反复出现、退让窗口持续至少 10 秒才生成压力通知，避免一次 GC 或短计算峰值产生告警。快照领取、构建、清理及事实补齐中的可重试锁竞争作为退让信号，立即暂停普通后台工作；至少三次观测且持续达到 10 秒才通知数据库压力，观测允许间隔不到 60 秒以覆盖事实轮询退避。SQL 超时、数据损坏和其他实际刷新失败仍立即报告，不当作正常锁退让。前台数据库操作耗尽预算而失败时也立即通知并暂缓后台工作。

同类持续异常在每个 Web / Worker 进程内合并为一次事件，通知发送成功后也不会每五分钟重复创建；同类异常连续五分钟没有再次报告后，新故障才重新提示。不同异常类型仍分别记录。接收人按 50 人分批处理；失败后保留待发送事件，重试复用通知 ID。该去重是进程内状态，不是跨节点统一事件库；数据库不可用时通知等待连接恢复，进程退出前尚未落库的提示不会持久化，诊断日志仍需由部署环境采集。

新增 SQLite `0067_queue_work_class_indexes.sql` 只建立队列领取索引，不转换业务记录或日志正文；全新建库、上一迁移升级、事务失败回滚及修复重跑有集成测试。PostgreSQL 无对应 schema 变化。没有新增外部服务，独立 Worker 显式复用仓库已有精确版本的 MIT `better-sqlite3` 驱动。发布物须包含 Web 日志线程和独立 Worker 的 `work-thread.js`、`read-model-thread.js` 及共享 chunk；打包脚本检查这些入口并复制原生驱动，离线 frozen-lockfile 安装和生产镜像启动纳入验收。

Full 升级应先排空并停止旧 Web/Worker，再统一升级所有节点。新版本保留执行 consumer 并创建后台 consumer，自动搬运旧队列中的后台消息；不要让旧版本与新版本同时修改 stream 配置。回滚前须排空新后台 subject，或停机保全并迁移其待处理消息，不能直接回退到只消费旧 subject 的版本。SQLite 回滚无正文转换，但需保留迁移记录和索引；按常规停机备份流程操作。源码更新后须重建自托管服务与工作线程，`pnpm test:integration` 会先构建 Web 线程入口。

进程崩溃、主机停机、内核 I/O 长期不返回、内存耗尽或数据库整体不可用仍需部署层健康检查和容量控制。这里的保证是已隔离路径不会在 Web 事件循环里同步扫描日志大库，并在可控的排队和执行边界降级；不能据此声明任意硬件故障或无限请求量下页面永远可用。

## 后台任务覆盖范围

| 当前入口 | 资源与优先级处理 | 验证层级 |
| --- | --- | --- |
| 执行派发、批次创建、定时触发 | 执行队列独立；Lite 批次构造与写事务进入执行线程 | 队列契约、调度应用/双数据库测试、500 槽位协议 |
| 领取、续租、完成、超时与轮次恢复 | 保留执行控制容量；网络恢复调用有期限；不因统计暂停停止运行 | Runner/应用/双数据库恢复测试 |
| JAR 导入及上传静态检查 | 有界解析、独立维护线程、持久作业与原子写入重试 | Lite/Full 解析集成、浏览器导入闭环、混合负载 |
| DDT 预览、导入、进度与完成写入 | 同一份解析和冲突规则；线程隔离；短锁异步退避 | 应用/双数据库测试、重复列与编辑恢复浏览器场景 |
| 分析导出 | 工作线程生成文件，原有权限与归属检查不变 | 应用/双数据库测试、CSV/JSON 作业及下载断言 |

## 验证入口

- `packages/db/test/attempt-log-store.integration.test.ts`：旧库只读、缺失文件、压缩、游标、去重和水位。
- `apps/web/server/log-io-pool.integration.test.ts`：约 128 MiB 旧库并发上传，以及持续卡住的读线程、HTTP 响应、队列上限和恢复。
- `packages/db/test/node-attempt-log-store.integration.test.ts`：真实 PostgreSQL 与独立日志线程验证两节点归属、转发、删除、重试与恢复。
- `packages/db/test/resource-priority.integration.test.ts` 和 `read-model-snapshots.integration.test.ts`：Lite/Full 锁竞争、查询期限、快照退让和恢复。
- `packages/application/test/runtime-notifications.test.ts`：通知权限、失败重试和稳定去重 ID。
- `packages/db/test/runner-heartbeat-contention.integration.test.ts`：真实 SQLite 写锁下的 8 Runner 心跳重试、原身份恢复和无工作时不争写锁；`apps/web/src/lib/runtime-priority.test.ts` 使用可控单调时钟模拟一天，验证孤立尖峰不刷通知、持续故障只提示一次、恢复后再次告警。这是确定性回归，不是实际运行 24 小时的 soak 验收。
- 队列共享契约验证执行/后台隔离、租约、确认、重试和死信；真实 JetStream 额外验证旧 subject 搬运，SQLite 验证十万条后台积压下实际领取 SQL 的索引计划。
- `file-parsing.integration.test.ts` 验证 Lite/Full 上传解析、重复列信息、队列过载与恢复。`worker-pool.test.ts` 验证线程意外退出时拒绝在途请求、退出前拒绝新任务、退出后重建以及忽略旧线程事件，防止等待中的请求永久占用工作槽。
- 应用及双数据库集成测试覆盖对象清理、保留策略、通知、Webhook 重试、定时触发去重、轮次恢复、DDT 取消和快照清理。控制面辅助循环（租约恢复、outbox、时钟同步）保留有界批次与已有恢复协议，不因后台暂停停止续租或完成上报。
- `pnpm test:background-resources`：先运行下述 Docker 验收，再启动两个 Full Web、两个独立 Worker 和真实 PostgreSQL/NATS/Redis/MinIO，各运行 10 项浏览器场景。混合负载包含 500 个用例协议执行、3 个各含 2,000 类的 JAR 导入、2 个各含 4,000 行的 DDT 导入及 CSV/JSON 分析导出，读取探针从导入入队前持续到批次创建、领取、日志上传、完成上报和所有后台作业终态，并验证导出文件内容非空。其余场景覆盖导入完整交互、DDT 编辑与恢复、统计缓存、权限/审计、通知和管理操作。`.github/workflows/distributed.yml` 的 `browser-background` 分区持续运行 Full 混合场景，并要求非空、无跳过、无重试的测试结果和 500 槽位响应报告。Docker 多核容量命令在有相应离线资源的验收主机运行。该命令不是强杀、断电或长时间 soak 测试；Full 故障矩阵仍使用既有 CI 验收入口。

- `pnpm test:runtime-resources`：从当前生产构建生成临时验收镜像，在 1 CPU/4 GiB、4 CPU/4 GiB，以及 4 CPU/无额外内存限制的容器中使用同样的 256 MiB 日志负载验证多核 CPU 时间、吞吐、RSS、读取正确性与独立 HTTP 探针；第三组观察独占主机内存充裕时的进一步扩展。随后在同一镜像中启动完整 Lite Web，运行 500 槽位 Runner 协议和执行记录页面探针。日志微基准中的 HTTP 探针是事件循环隔离测试，完整 Web 响应由后续协议验收覆盖。

容器验收要求本机至少 4 个可用 CPU，已安装构建依赖、浏览器与内置 Agent 资源，并已离线加载 `deploy/docker/backend.Dockerfile` 指定的固定 Node 基础镜像。可通过 `AUTOFORGE_RESOURCE_TEST_CPUS` 调整多核组配额；1 核组必须准确识别 quota，多核组平均 CPU 时间必须超过 1.2 核、吞吐至少提高 10%，并满足 HTTP P95 小于 1.5 秒与 RSS 小于容器内存的 80%。压测独占端口 3100，应在空闲验收主机运行。结果保存在 `test-results/runtime-resources`；它证明指定负载下的横向 CPU 利用能力，不代替生产硬件长期 soak 或真实 JVM 容量测试。

Docker 浏览器夹具使用 Linux host 网络访问宿主机上的本地 Webhook 接收器，并只对临时测试目录使用可共享的创建权限，使容器内的非 root 用户可以删除宿主侧创建的测试对象。生产 Compose 的网络、用户和目录权限不因此改变。
