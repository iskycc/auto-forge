# 运行时压缩包缓存

任务执行与公开日志重跑共用以下链路；业务快照、租约、输入摘要仍是执行依据，缓存不改变批次选包规则。

## 下载路径

- 上传型 JDK/依赖压缩包：Lite 从本地对象存储、Full 从 MinIO 流式读取，经控制面发送给 Agent。
- URL 型压缩包：控制面先验证 Runner 身份、有效租约及输入是否在 assignment 快照中，再由主平台下载到本节点 `AUTOFORGE_DATA_DIR/cache/runtime-archives/v1/`。大小和 SHA-256 全部验证通过后才原子发布并分发；未验证的半文件不会发送给 Agent。
- URL 必须是主平台可访问的 HTTP(S) 地址，不带用户名/密码，不跟随重定向，也不转发 Runner 凭据。断网运行时应使用上传资源或可访问的内网文件服务；缓存不能代替离线资源交付。
- Full 各平台节点各自维护可重建的本地 URL 缓存，不依赖 Redis 锁、共享挂载或新的数据库写入；经 Nginx 命中另一个平台节点时，该节点首次可能需要下载。已上传资源仍通过共同的 MinIO 读取。

主平台同一摘要/大小的并发请求合并，每节点最多两路下载或缓存校验、最多 64 个不同的在途缓存请求，单次源站下载最多 10 分钟。请求断开不会取消其他 Agent 共用的下载。以流式读写、哈希和背压控制内存，不把压缩包完整读入 Web 进程。

主平台缓存使用文件修改时间持久化最后使用时刻，24 小时未使用的文件在启动后的首次访问或后续缓存维护中清理。保留容量目标为 32 GiB、10,000 项，容量紧张时淘汰没有请求正在使用的旧缓存。单个更大的合法压缩包允许独占缓存，实际可用空间与任务配额仍必须满足；并发占用导致暂时无法接纳时返回明确下载错误。这里的容量目标不是上传文件大小限制。

## Runner 生命周期

`AUTOFORGE_AGENT_DATA_DIR/cache/runtime-inputs/v1/<sha256>-<size>/` 保存：

- `archive`：通过大小与 SHA-256 校验的压缩包。
- `usage.json`：格式版本及 UTC 最后使用时刻，临时文件写入、fsync 后原子替换。

只对 `jdk-archive` 与 `jar-bundle` 启用跨批次缓存。每次任务使用时，从本次使用重新计算 24 小时，包括同一批次中继续执行的用例。Runner 启动后及每五分钟清理过期或未完成的缓存；读取时立即检查过期，因此不必等待定时清理。清理跳过正在下载、校验或复制的项。重启不删除有效缓存，批次关闭只删除 `work/batches/<batch-id>/`。

相同摘要的并发使用合并下载，不同摘要可独立下载。命中时再次校验内容；损坏、过期或缺少完整使用元数据时重新通过控制面获取。压缩包复制进批次/attempt 工作目录，不与持久缓存硬链接，防止用例修改工作文件污染后续批次。解压结果仍只在同批次内共享，并按原有终态确认机制清理；本次没有增加跨批次解压目录复用。

Runner 缓存最多接纳 32 GiB、10,000 项，并为压缩包与工作副本检查可用空间。容量不足以同时保留缓存和副本时，直接通过控制面下载到当前工作目录，不因可选缓存容量不足拒绝执行，也不提前淘汰仍在 24 小时有效期内的已有缓存。工作目录本身的磁盘配额和可用空间不足仍会明确失败。缓存目录与日志 spool 独立，不挤占 spool 的逻辑配额；部署仍需为整个 Agent 数据盘配置实际容量和监控。

## 版本与升级

缓存键包含 SHA-256 与大小，不使用 URL、文件名、项目版本名或批次 ID。上传新包或重新登记 URL 后，新批次使用新快照及新摘要，不会混用旧 JAR；依赖包仍须包含全部执行类和依赖。已在运行的批次继续使用其原快照。仅替换 URL 对应的文件、却不更新登记的 SHA-256/大小，不会改变已经固化的执行内容。

先升级主平台，再升级 Runner。新主平台不向旧 Runner 下发 `downloadUrl`，旧 Runner 会通过已有控制面输入端点下载；升级 Runner 后才启用新的 24 小时跨批次缓存。新 Runner 始终通过控制面下载，旧平台的 URL 输入端点不具备代理能力，因此不能先单独升级 Runner 来获得此行为。Adapter 无需参与下载或维护缓存，也无需修改用例参数。

验证覆盖：Runner 重启/续期/过期、跨终态批次复用、并发与取消、摘要损坏恢复、工作副本隔离；平台缓存并发、失败恢复和版本内容隔离；SQLite/PostgreSQL 有效及无效租约；本地/MinIO 流式读取；HTTP 输入路由的鉴权和缓存复用。
