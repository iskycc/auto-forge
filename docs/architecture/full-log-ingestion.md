# Full 日志上传与独立持久化

Full 的日志上传准入为整个部署共享 **1,000 请求／秒**，由 Redis 原子计数，不按 Web 副本数量相乘，也不再受节点每分钟槽位总额度限制。单次 attempt 的异常高频保护、HTTP 请求体上限、凭据与租约校验保留；续租、领取、完成和产物不共用日志额度。Lite 沿用按认证槽位计算的内存额度与本地日志写入，不加载 NATS 或 Redis。

## 写入和确认

1. Web 校验 Runner 凭据、共享准入、attempt 所属关系及租约，然后清理凭据格式的日志内容。
2. 已授权日志以服务端随机对象键写入 MinIO 的 `log-ingestion/v1/` 暂存目录，记录大小和 SHA-256。暂存内容没有 Runner 凭据或 lease token。
3. Web 向独立 JetStream 持久流发布小型引用消息，包含协议版本、稳定消息 ID、attempt ID、创建时间、对象键、大小和摘要。正文不放进消息，也不进入原有调度队列。
4. Web 备用消费者和每个独立 Worker 各有最多八个日志写入操作，共享一个显式确认的持久消费者。Worker 读取并校验对象，继续通过原日志仓储路由到已登记的 PostgreSQL 日期库。归档只读保护、日期归属、跨库位置、序号去重和连续水位不变。
5. 日志正文事务及主库确认水位完成后，消费者才回复 Web。Web 沿用 Runner Protocol v1 返回真实确认水位；入队和 MinIO 写入成功不代表日志已确认。JetStream 随后确认，暂存对象再删除。

Agent 在收到水位之前仍保留本地 spool。消费者、Web 或网络在任意阶段中断时，可以重投或由 Agent 重传同一序号；数据库继续按原有约束防止重复或内容冲突。Redis 及队列不作为已确认日志的唯一事实来源。正文的读取方式、公开日志权限和执行完成校验保持原样，无需新的 Runner 协议。

## 资源与故障边界

- Web 日志持久化使用独立的八连接业务池；日志正文与日期锁的连接池各最多八连接。领取、续租及完成继续使用原控制池。独立 Worker 也提供日志消费能力，不占用导入、AI 或调度消息槽位。
- 每个 Web 最多接收 256 个在途上传，编码后的在途正文总计最多 64 MiB，单个暂存对象最多 4 MiB。超过本地接收容量返回明确繁忙错误，不无限排队。HTTP 等待结束后，尚未完成的底层 I/O 仍占用这些额度，直到实际结束，避免存储故障时不断接收替代请求。每秒请求准入与字节容量是不同的保护条件。
- JetStream 流名 `AUTOFORGE_LOG_INGESTION_V1_PLATFORM`，subject 为 `autoforge.logs.v1.ingest.platform`，持久消费者 `autoforge-log-writer-v1`。使用文件存储、WorkQueue 保留、64 MiB 引用容量、五分钟消息期限；容量不足时拒绝新消息，不淘汰旧消息。
- 启动时校验已有日志流的文件存储、保留策略、拒绝新消息策略及唯一 subject；配置不兼容则明确失败，不悄悄降为内存队列或淘汰未处理日志。容量、消息期限及大小限制按版本化配置更新，保留部署方设置的副本数和更严格的消息数量限制。
- 确认等待十秒、全局最多 256 条待确认，处理期间每三秒延续消息处理状态，最多投递八次；临时写入失败有界退避。正文未成功写入时不返回成功水位，Agent 继续持有未确认日志。
- Web 从开始暂存到收到持久回执的整个等待最多四秒，早于 Agent 五秒的实时上传等待；超时返回繁忙，不伪造成功。服务关闭时同样及时结束等待。超时或关闭后才完成的暂存不再入队，直接清理；已经发布的引用仍由消费者持久化。完成了正文写入但回执丢失的请求可安全重传。暂存删除失败不能反过来改判已经提交的日志写入。
- JetStream 的明确拒绝会立即清理对应暂存对象，避免队列已满时反复上传放大磁盘占用；网络超时的发布结果不确定，保留对象。后台每 30 秒执行一次有界扫描，逐次最多十页、每页 200 项，只删除已超过十五分钟的暂存对象。该期限大于引用消息五分钟保留期；清理不触碰最终日志、产物、归档或其他对象前缀。
- PostgreSQL 按日存储已发布批次大小后，不再对同一批次额外写入零值，减少批跑上传争用同一行。旧固定日志库仍按持久化结果更新大小，并只在大小增长时写入。

每秒 1,000 次是部署准入额度，不等同于任意正文大小、任意硬件下的持久化吞吐保证。应同时检查正文大小、日志数据库延迟、队列待确认量、Redis 和 MinIO 状态。大规模扩容时须按 Web／Worker 数量及最多同时打开的日期库数量核算 PostgreSQL 的总连接预算。

## 部署与兼容

继续使用 Full 现有 PostgreSQL、Redis、NATS JetStream 和 MinIO，无新增服务或外部依赖，无数据库迁移。Web 与 Worker 一起升级后自动创建日志流和消费者，不需要额外启动命令。NATS 账号需要创建该流／消费者、发布引用和订阅内部回执 subject 的权限。

Lite 仍由共享应用用例完成认证、脱敏及确认，然后直接写本地日志；应用层只依赖可选持久化端口，没有基础设施客户端或散落的模式判断。本变更未增加日志分页、修改用例状态机或调整执行超时。

## 验证范围

Runner 凭据及租约必须在暂存前通过验证，消息和暂存不能包含这些凭据。Redis 用独立客户端验证总额度共享及第 1,001 次拒绝，受控时钟验证一秒后恢复额度。真实 JetStream 配合原本地日志仓储覆盖落库前不确认、瞬时故障重投、重复／乱序／冲突、等待超时后重传、三个连接共同消费、归档只读拒绝和队列满后的暂存回收。内部消息分别携带 ExecutionRun ID 和 RunAttempt ID，不混用。
