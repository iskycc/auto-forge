# 数据库写入竞争排查与恢复边界

本轮排查覆盖 `packages/db` 的 SQLite/PostgreSQL 仓储、SQLite 队列、批次日志库，以及 Web/Worker 的后台维护与异常通知入口。重点检查：读后升级写锁、未处理的短暂锁冲突、事务外副作用、空轮询写入、批量加锁顺序、错误分类和连接释放。排查覆盖范围不代表数据库可以无限并发写入。

## 已修复的问题

| 范围 | 原因 | 处理 |
| --- | --- | --- |
| Lite 分析任务、认领、释放、开始和完成分析、截图元数据 | Web 连接只等待 25ms，但这些写入口没有与执行仓储一致的锁恢复；正常后台短事务也可能让首次操作失败 | 原子语句重试；多语句操作从 `BEGIN IMMEDIATE` 重试完整事务，每次重新验证状态与归属 |
| Lite 用例元数据、版本恢复、来源生命周期、DDT 编辑/模板/回收站 | 部分写入直接执行，或事务入口未覆盖瞬时写锁 | 在仓储的原子写入边界补齐有限异步重试；不重放整个 HTTP 请求 |
| Lite 用户、角色、成员、会话、LDAP、项目版本和运行时配置 | 管理操作与调度、快照共用主数据库，写入口的恢复策略不一致 | 保留权限、版本和唯一性校验；本地用户创建在同一写事务内检查重名并插入 |
| Lite 执行机生命周期、分组、安装配置、轮次恢复、Webhook、计划触发、通知和保留清理 | 写入口存在同类遗漏 | 补齐原子写入恢复；保留空任务的只读探测；网络投递和日志文件删除仍在数据库事务之外 |
| Lite/Full API Key 鉴权 | 每次查询都写入活动时间，Full 还锁定令牌行；频繁轮询把只读鉴权变成热点写入 | 权限、停用、撤销和过期仍逐次读取；活动时间最多每 5 分钟更新一次。Lite 遇写锁延后记录，Full 使用 `SKIP LOCKED`，不因非关键活动时间更新失败拒绝有效令牌 |
| Full 原子语句与多语句写入 | 单条写入和重复的事务包装没有统一处理死锁、序列化失败和锁超时 | 自动提交的原子写入可单独重试；通用 SQL/Drizzle 事务在回滚并释放连接后有限重试；业务冲突和约束错误不重试。手工管理完成回执的执行快路径保留原有幂等上报恢复，不包住提交后的逻辑整体重放 |
| Full DDT 并发导入和编辑、批量分析 | 不同输入顺序可能造成相反的加锁顺序；并发导入不存在的 CaseID 还可能同时通过存在性检查 | DDT 编辑按稳定顺序预锁现有记录；导入按规范化 CaseID 顺序写入，用作用域内唯一键处理并发新增，避免把无交集的导入锁在整个项目/版本/阶段上；分析认领排序插入，完成分析同时按顺序锁定来源与目标。返回顺序、导入覆盖顺序和编辑版本冲突语义保持不变 |
| Full 数据库连接 | 普通连接没有锁等待与语句执行期限，异常事务可能长期占住连接池 | 默认单次锁等待 1 秒、单条语句 30 秒；专用后台连接继续使用更短的显式配置。启动迁移在 readiness 之前运行，不使用请求期限，提交后恢复连接默认值 |
| API 和服务账号错误分类 | PostgreSQL `40P01`/`40001` 被映射成普通 500；服务账号其他数据库错误被误报为重名 | 耗尽恢复预算的锁竞争返回 `503 PLATFORM_BUSY` 并进入原有诊断通知；仅唯一性错误转换为服务账号重名 |

## 保留的约束

- SQLite 主库写入仍为单写者，WAL 允许读请求继续访问已提交数据。Web 的同步等待仍为 25ms，不延长到数秒；最多尝试 6 次，退避为 25、50、100、200、400ms。退避让出事件循环，不把所有管理请求放入一个长期持锁事务。
- PostgreSQL 原子写入和通用事务最多尝试 6 次，仅恢复 `55P03`、`40P01`、`40001`。语句执行超时、网络断开、约束失败和业务版本冲突不会自动重放。手工 SQL 事务的回滚失败时丢弃连接，并保留原错误与回滚错误；Drizzle 事务仍由 ORM 负责回滚与连接释放。
- 只有数据库回滚能够撤销的操作进入事务重试。对象存储、Webhook/Jenkins 请求、日志文件清理和其他外部副作用不随数据库事务重试。
- 队列、快照领取/清理、通知生成、分析事实补齐、Webhook 领取和轮次恢复在没有待处理工作时继续只读探测。已有心跳重试、执行状态机版本保护、完成回执、日志水位和 Runner spool 重传继续生效。
- API Key 的“最近使用时间”是合并后的活动记录，不是逐次请求审计。持续争用时记录可能更晚补齐；鉴权失败不会被吞掉，权限不缓存为业务事实。
- 耗尽预算仍返回明确失败；数据库不可写时通知也可能暂时无法落库。原有运行诊断保留后台操作名/工作线程任务名、数据库、请求等上下文，并在恢复后发送、合并持续异常，不用删除告警掩盖争用。

## 验证方法

1. 使用两个真实 SQLite 连接，另一连接先持有写事务，必须等事件循环让出后才能释放。分析、DDT 生命周期、身份权限、项目配置、执行机分组和公开日志分享契约都在这一条件下验证。
2. 保留已有八 Runner 心跳、持续占锁后的恢复、空闲后台不取写锁、SR 分类版本冲突等回归。
3. 使用真实 PostgreSQL 制造双事务反向加锁死锁和锁超时，检查整笔回滚、重试次数、连接可继续使用、约束错误不重试；回滚连接断开使用单元测试验证销毁及错误保留。
4. 同一 DDT 作用域以相反顺序并发导入和编辑，验证没有重复用例、导入结果保留输入顺序，两个过期版本编辑只允许一个成功，失败编辑不留下部分数据或历史记录。保持一个文件事务未提交时，无交集的另一文件仍能导入；重复 CaseID（含大小写变体）的覆盖顺序、历史 ID 和冲突时整文件回滚保持原语义。
5. Lite/Full API Key 在持锁下验证有效鉴权、活动时间合并、令牌撤销写入恢复和撤销即时生效；错误映射验证不泄漏数据库语句及凭据。

这些测试针对可重复的竞争与恢复路径，不能替代生产数据规模、磁盘延迟和持续负载的观测。长时间外部写事务、DDL、磁盘故障或超出主机容量时，目标是有界失败与可恢复，而不是承诺任何负载下都没有锁等待。

新增 PostgreSQL 事务竞争与 API Key 持锁测试已加入 `scripts/quality/test-full.sh` 的适配器阶段；其余 SQLite 持锁契约随常规集成测试运行。
