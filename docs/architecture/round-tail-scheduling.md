# 轮次尾部补位与末轮渐进初析

## 两轮调度窗口

整轮重跑仍由同一个执行批次管理。`current_round` 表示最新已经开放的轮次，不能作为完成结果的归属来源；每条 `execution_runs.execution_round` 决定下一次实际尝试的轮次，创建 assignment 时原样写入 `run_attempts.execution_round`。完成、历史、统计和导出继续读取尝试自身的轮次。

本轮全部待调度用例已经分配之后，如果仍有在途用例、下一轮存在已确认需要重跑的用例，可以使用任务剩余槽位提前执行下一轮。所有轮次共享任务、项目和执行节点的原有并发及资源额度，不给每轮另开一份额度。

窗口遵循以下约束：

- 只开放紧邻的下一轮；没有实际失败重跑成员时，不建立空轮次、不推高轮次编号。
- 最新轮次仍有未分配成员时，先调度这些成员；不能越过它开启后续轮次。
- 只要更早一轮还有 assigned／running，不能再开放第三轮。例如第 1、2 轮重叠时，第 2 轮再次失败的用例扣留到第 3 轮，直到第 1 轮全部结束并且第 2 轮没有待调度成员。
- 第 1 轮晚完成的失败用例仍加入第 2 轮，不能因为第 2 轮已经开始而直接跳到第 3 轮；它们会阻止窗口继续推进，直到分配完成。
- 两轮重叠时，共享并发上限取这两轮已配置并发的较小值；`可新增槽位 = max(0, min(旧轮并发, 新轮并发) - 所有轮次的 assigned/running 数)`。旧轮 50、新轮 30 时，旧轮在槽数达到或超过 30 不补槽，降到 29 才能补 1 个；旧轮 30、新轮 50 时，重叠期间同样最多合计 30 个。旧轮完全排空后，才采用新轮完整额度。收紧额度不终止已经分配的用例。
- Jenkins 轮次环境恢复仍是完整屏障，上一轮全部在途用例结束后才能触发，恢复成功并经过等待期限后才释放下一轮。
- 下一轮动态并发规则依赖上一轮通过率或剩余数量时，等待完整结果再判断；仅按轮次指定固定并发的规则可以参与补位。
- 暂停时不开放新轮次、不释放扣留；继续调度后重新判断。终止关闭等待用例，不能被迟到完成或重放重新打开。

Lite 在原有短写事务中更新；Full 在批次行锁内判断。Full 完成上报保留普通成功路径的快速提交，只在确实存在扣留且没有可分配成员时进入尾部判断。调度开始和分配结束时也会检查窗口；补位调度的无扣留／受阻探针只读，不申请 SQLite 写锁。新的在途轮次部分索引限制尾部检查的扫描范围。

重叠并发读取 `run_batch_round_concurrencies` 的旧轮实际配置，不能用其当前在槽数量代替，也不能用最新动态并发状态覆盖旧轮额度。缺少轮次配置记录的历史批次回退到批次基础并发。轮次历史仍记录该轮完整配置值，避免把临时较小额度永久写入新轮；调度计划、候选批次发现、数据库原子预留和并发诊断使用同一限制。Full 在取得批次锁后重新读取额度，两个调度器不能因使用旧计划重复占用最后一个槽位。预留请求同时携带计算计划时的批次轮次；事务发现窗口已经推进时拒绝旧计划，后续调度重新取数，避免动态并发新状态尚未激活时沿用旧额度。

Jenkins 恢复的 idle、pending、polling、waiting、failed 状态均不允许提前补位；即使恢复状态已经是 succeeded，只要上一轮仍有在途用例，也必须等待旧轮排空。恢复成功后的放行只开启正常下一轮调度，不绕过暂停、终止或两轮窗口。

旧轮因执行节点失联等基础设施故障进入同轮重试队列时，仍属于未结束轮次；即使暂时没有旧轮 assigned／running，也保留旧轮并发限制，直到这些同轮重试结束。正常失败已经转入新轮的成员不再计作旧轮等待。

## 末轮自动 AI 初析

任务原有的“执行结束后 AI 初步分析”开关保持默认关闭。开启后，整轮模式进入最后允许的轮次时即可幂等建立自动作业；立即重试模式在出现最终失败成员后建立。批次提前终止时仍保留终态自动扫描兜底。

只有已经结束、后续不会再重试的失败／超时成员进入作业。还在执行、排队或者等待下一轮的用例不会提前送给模型。人工整批初析仍需等待批次终态，单次尝试初析保持原权限和行为。

自动作业按以下周期推进：

1. 每页最多接收 100 个已最终结束的成员。通过持久成员清单排除已接收项，不以 run ID 水位排除迟到的低 ID 成员。
2. 采集这些成员的证据，沿用完整堆栈精确分组、stdout 全文规则、颜色清理、字符裁剪及受限 tools。
3. 处理并发布这一批的共同建议。在途组全部完成后才开启下一轮接收周期，避免重置正在运行的模型调用或租约。
4. 批次仍在执行时，作业保留并等待至少 15 秒再扫描；已发布建议可立即查看和导出。进度总数随最终失败成员进入而增长，不代表整个批次的用例总数。
5. 同栈小组增加成员时，重新合并全部成员全文并统一回填建议；精确堆栈组达到 10 例并已有共同建议后，新成员复用该建议，不重复请求相同堆栈。回填分批进行，不重复累加已完成计数。发布代次防止旧周期迟到写入新周期。
6. 批次终态后，在写入本页清单的同一事务内复核是否还有遗漏成员，防止读页和任务结束竞争导致提前关闭接收；因排队超时等原因没有实际尝试的最终失败也保留为证据不足项，不向模型发送空日志，再关闭接收并完成作业。没有最终失败的批次不调用模型。AI 作业取消后不再自动重建，执行任务继续独立运行。

AI 仅使用空闲后台预算：Web、调度、续租、日志与完成上报优先。模型端点并发／RPM／TPM、冷却、重试、权限复核、租约与崩溃恢复沿用现有机制。Lite 使用独立线程、SQLite 持久队列及本地证据对象；Full 复用 PostgreSQL 作业／outbox、NATS 唤醒、Redis 可重建进度缓存与 MinIO 证据对象，不在执行完成事务内调用模型或读取完整日志。

## 升级与恢复

SQLite `0099_round_tail_and_progressive_ai.sql`、PostgreSQL `0098_round_tail_and_progressive_ai.sql` 增加接收状态、下次扫描时间、发布代次和索引。既有人工／自动作业默认关闭持续接收，原结果及成员不变；升级后新建的自动作业才使用渐进接收。

Full 部署更新时，Web 与所有 Worker 应使用同一版本，避免把新旧轮次恢复逻辑混用；Runner Agent 协议未改变。

升级前按现有流程备份主数据库。迁移失败时由迁移事务回滚，修复原因后重启重试。恢复旧程序前先停止新 AI 作业并等待在途 AI 调用排空，保留原始日志；新增列和索引可保留，不应手工删除已发布结论。旧程序不理解持续接收，因此不能让旧 Worker 继续消费仍开放接收的新作业。执行结果与日志不依赖 AI 状态。

## 故障复查与恢复矩阵（2026-11-10）

第二次故障复查发现并修复了三个故障恢复遗漏，并补齐一项旧配置兼容：

1. 完成事务已提交、释放事务尚未提交时进程退出，或者最后一条原轮次 assignment 提交后尚未执行尾部检查就退出，可能留下没有普通可调度成员的扣留批次。全局周期扫描及 Runner 领取扫描现在也会发现符合两轮窗口的持久扣留工作；候选探针不改变执行事实，实际释放仍在事务内重新校验。等待第三轮、暂停、终止、尚未完成的 Jenkins 恢复和依赖上一轮统计的规则不会占用可分配批次窗口。
2. Jenkins 等待结束回调原来直接释放成员并覆盖批次轮次。现在统一调用轮次推进实现；暂停、终态、上一轮仍在途或者批次已经推进时只记录恢复完成并释放恢复工作租约，不重新启动、倒退轮次或绕过两轮屏障。继续调度后可直接使用已完成的恢复结果，不重复触发 Jenkins。
3. 全部用例结果已提交、批次终态聚合前退出，且后续没有 Agent 重放时，普通批次也可能残留执行中。周期生命周期维护现在会在没有排队／在途成员且成员数等于执行快照总数时重新聚合终态；不依赖另一条领取或完成请求，也不会把只生成部分成员的批次判为结束。
4. 旧任务快照可能使用 `executionRoundFrom`／`executionRoundTo`，不能绕过已有规范化实现直接读取新字段。轮次屏障现在复用原规则规范化语义，扫描探针也识别旧触发轮次；缺省／非数组的旧规则值沿用既有读取行为，不使调度抛出类型异常。

排查现场时可先按具体批次聚合下列事实；只查轮次和状态，不加载日志或所有 attempt 正文。`<batch_id>` 应通过数据库客户端的绑定参数传入：

```sql
SELECT execution_round, status, held_round, COUNT(*) AS run_count
FROM execution_runs
WHERE batch_id = <batch_id>
GROUP BY execution_round, status, held_round
ORDER BY execution_round, status, held_round;
```

`held_round=0` 才可直接分配；assigned／running 所在的最早轮次决定能否向后滑动窗口。批次的 `current_round` 是最新开放轮次，不能据此推断所有运行中用例的归属。

新增的[轮次结束条件](./unlimited-task-retries.md)也是完整统计屏障：配置该轮的结束规则时，下一轮不能提前补位；该轮排空后先判断结束条件，再决定是否触发 Jenkins 恢复及释放下一轮。没有结束条件的轮次保持现有两轮补位逻辑。
