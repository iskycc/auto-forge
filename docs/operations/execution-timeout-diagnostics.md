# 执行超时与日志上传诊断

## 日志上报超时

有 `settings.manage` 权限时，在“平台设置 → 平台配置 → 容量、会话与调度阈值”设置“日志上报超时（秒）”。`0` 关闭保护，旧配置默认 `0`。设置 `120` 时，Runner 从 Java 启动或最近一次收到 stdout／stderr 起，连续 120 秒没有输出就强制终止该执行进程组，并以 `EXECUTION_LOG_SILENCE_TIMEOUT` 记录为超时。总执行期限先到或相同时，记录为原有的执行超时。对于正常用例长时间静默的环境，按实际静默周期设置阈值。

监测依据为本地管道的实际输出，上传确认、日志限流、网络重传、Agent 诊断和日志字节上限均不改变这一计时。进程终止后仍按上传阶段的时限和日志确认水位收尾。提前到达的静默期限也可触发一次有界的超时前线程快照。

保存后用于新派发的尝试，已派发的规格保持原值。Lite 和 Full 使用同一可选 Runner Protocol 字段，未更新的 Agent 会忽略该字段。Full 分布式部署通过各节点的配置文件管理 `limits.caseLogSilenceTimeoutSeconds`，按部署流程同步配置。没有数据库迁移。

## 两类提示分别表示什么

`TestNG exceeded the configured execution timeout.` 是 Agent 的本地进程执行期限触发。`Execution exceeded its configured timeout.` 是平台依据该 attempt 的领取／开始时间和执行期限进行恢复。两者都不能单独证明 OOM、Java 死锁或者被测接口超时。

本轮排查用户提供的 `POST /api/v1/run-attempts/<id>/logs`、`429`、`durationMs:0`，确认是执行机上传在入口被限流。旧策略所有槽位共用每节点每分钟 600 次，而实时上传按每例约 500ms 运行；十个持续产生日志的槽位正常就需要约 1200 次／分钟。这会让后来的用例日志断更，并不证明 Java 停止输出。旧策略在本地以正常上传频率复现了第 601 个请求被拒绝。

还复现了阶段登记过晚：Java 已结束后，Agent 先排空日志，再调用产物声明进入上传阶段。日志被限流时，平台仍把等待上传的时间算进用例执行，可能出现不准确的执行超时。现在进程正常结束后先通过原有的空产物声明进入上传阶段，再处理报告和日志；不需要实际配置任何产物。执行超时和上传超时仍独立，真正到达 Java 期限的尝试不会改判为正常完成。

## 页面入口

- 公开日志页的超时描述显示“超时诊断”，已登录用户可点击“查看超时诊断”，直接打开现有日志终端的 **Agent 诊断** 流。
- 执行详情中的节点超时记录也提供相同入口。
- 未登录公开页保留公开结果描述，显示“登录查看超时诊断”；实际诊断读取继续要求登录及该项目的 `log.read` 权限，没有扩大公开链接的访问范围。

正常控制面回收的超时描述包含配置期限、从领取记录计算的时长、判定时间、最后续租及租约期限、节点最近心跳。它不读取主日志正文，不在恢复事务中访问日志数据库、MinIO 或外部进程。

Agent 的超时摘要和诊断流还包含 Java 启动时间、最后 stdout／stderr 时间与产生字节数、已静默多久、上传请求数、429 次数、最后成功上传时间和最近上传错误。受权限保护的 Agent 诊断流额外记录本例实际环境 IP，以及从 `/proc` 取得的 PID、Linux 状态、线程数和进程常驻内存。多个节点的超时可按环境 IP、最后输出和栈顶位置对照。进程状态 `D` 表示不可中断的内核等待，`S` 或单次常驻内存快照本身不足以确认卡住或内存不足。

## JVM 快照及性能边界

Agent 每次尝试仅在接近平台执行期限时采集一次：提前量为执行期限的十分之一，最多提前 15 秒。完成的尝试会取消定时器。每个节点同时只采集一个 JVM；期限仍有余量时，同节点其他尝试最多等待 4 秒，结束或取消时立即退出等待。即使工具名额没有空出，尝试仍会记录已取得的 Linux 进程快照。

通过进程 PID 和内核启动标识确认仍为原尝试后，优先使用该 Java 所在 JDK 的 `jstack -l`。项目上传的 JDK 归档在解压时只给 `java` 启用执行权限，旧 Agent 直接运行 `jstack` 会收到 `permission denied`。新 Agent 通过同一 JDK 的 Java 启动诊断入口，JDK 8 使用 `lib/tools.jar`，模块化 JDK 使用 `jdk.jcmd`，新旧解压缓存均可使用。命令采用参数数组、独立进程组和受限环境，不继承 Agent 凭据；总采集期限两秒、有限 JVM 堆、64 KiB 输出上限。线程快照写入独立 Agent 日志流，沿用秘密过滤、spool、确认重传和归档。

有明确证据时摘要标出 Java 锁等待、网络读取、线程／任务等待或死锁，并保留相关栈帧；RUNNABLE 不直接判定为 CPU 忙等。一次快照仅是现场证据，无法自动证明所有业务根因。完整快照可在同一诊断终端查看及搜索。

运行时缺少诊断组件、Attach 被禁止、权限不足、采集超时或容器 JVM 无法直接诊断时，显示具体不可用原因，查看 Agent 流可获得工具输出。Linux 进程快照和取栈均无需 cgroup v2。续租、用例执行期限及终止由既有链路处理，诊断依赖现场进程及日志上传仍可用。

线程快照采用单个有界 Agent 日志块发布。暂存空间不足等持久化失败会记录在 Agent 后台及超时摘要中，不把失败快照留在正常日志的待写队列，不制造序号缺口，也不因此把原用例改判为日志保存失败。正常 stdout／stderr 的存储错误仍按原规则明确失败，不能借诊断的可选写入隐藏实际业务日志丢失。

## 限流及双模式

日志、完成、续租与产物声明分别限流，互不共用额度。每个 attempt／lease 保留独立入口额度；Lite 的节点总额度按数据库中已认证的 `maxConcurrency` 计算，正常 2Hz 日志上传保留 50% 槽位余量及原最小额度。Full 日志改为整个部署共享每秒 1,000 次准入，不再使用原有节点分钟额度；日志正文经过 MinIO 暂存和独立 JetStream 消费者持久化，收到真实提交水位才确认。请求头和请求体不能提高额度；实现及故障边界见[Full 日志上传](../architecture/full-log-ingestion.md)。

Lite 使用原内存限流器及 SQLite／本地日志存储；Full 使用 Redis 共享计数、PostgreSQL 执行状态以及已配置日志库。没有新增数据库迁移、外部依赖或 Runner Protocol 字段。

Web 和所有 Worker 需要一起更新；线程快照及进程阶段提前上报还需要更新 Runner Agent。旧 Agent 仍可连接新平台并使用修正后的限流，但不会凭空补出历史线程快照。旧执行结果原样保留，不把后续节点状态回填为当时原因。

## 验证方法

- 使用固定窗口模拟十槽位、每例 120 次／分钟的正常上传，并验证单例过量、节点总量和续租／完成独立额度。
- Runner 回归先复现“日志限流时尚未进入上传阶段”，再验证 Java 结束后先登记阶段、仍能完成日志及结果；SQLite／PostgreSQL 验证空产物声明后适用上传期限。
- 用真实 Java 8／21 运行持锁程序，将 `jstack` 设为与项目 JDK 解压后相同的权限，验证取到业务线程 `BLOCKED` 栈且原 JVM 正常结束。另验证输出预算、上传 429、被取消的定时器和同节点采集名额被占用时保留的进程快照。
- Playwright 使用已持久化的超时记录和诊断日志检查公开页面、登录权限、诊断终端、1024px／1536px 和深浅色布局。

上述信息用于继续定位真实业务卡住的位置；修复日志限流及阶段计时，不等同于已经复现并解释用户现场每一个本地 JVM 超时。

## Full 日志队列接入后的再次审查

2026-11-16 对当前 71 个本地变更文件再次检查。除上表的锁、计时及诊断修复外，新增部分服务于 Full 每秒 1,000 次共享准入和独立日志持久化：应用端口与内部契约、Redis 准入、MinIO 暂存、JetStream 消费、Web／Worker 组合根及独立连接池。新增的 workspace 依赖仅连接已有领域包，没有引入新的外部依赖、数据库迁移或运行组件。Lite 仍直接写日志，不加载这些 Full 客户端。

审查额外复现并修复了三个故障边界，对应三项真实 JetStream 测试在修改前失败，修改后通过：

1. 原确认定时器在 MinIO 暂存完成后才开始，暂存卡住时 HTTP 等待没有该期限保护。现在四秒期限覆盖暂存、发布和回执等待，早于 Agent 的五秒实时上传等待；已经超时的底层 I/O 仍占据有界额度，直到实际结束，防止故障时无限接收替代上传。
2. 服务关闭时，正在暂存的请求原本不在待回执集合中，不能及时收到可重试结果。现在关闭会结束这些 HTTP 等待；随后才完成的暂存不再发布引用，执行清理。已发布的引用继续遵守落库后确认、重复安全的原规则。
3. 已存在的日志流原本没有重新校验持久化语义。现在拒绝内存存储、错误保留策略、淘汰旧消息或错误 subject，按版本恢复可变容量和期限配置，同时保留部署方的副本数及更严格的消息数限制。
