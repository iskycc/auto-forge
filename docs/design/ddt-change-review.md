# 个人 DDT 变更审核

个人调试数据通过申请合入当前项目、版本和测试阶段的正式 DDT 库。TestNG JAR 仍使用原有正式库导入流程。

## 使用流程

1. 在“用例调试 → DDT 调试”上传表格、复制或编辑个人数据，然后点击“提交变更”。
2. 按 CaseId 查找并勾选有差异的用例，填写标题和可选说明。“选择字段”显示正式原值和拟合入值；已有用例可以排除个人账号等不应共享的字段。新增用例提交完整数据，用户旅程按完整旅程字段选择。
3. 提交后，个人数据继续独立保存。修改个人数据不会改变已经提交的申请。可在“我的申请”查看结果、撤回待审核申请。
4. 具有当前项目 `case.manage` 权限的用户在“用例管理 → DDT 管理 → 变更审核”查看全部申请、展开差异并填写意见。审核合入、退回修改均需确认，退回原因必填。普通用户只可查看自己的申请。
5. 合入后保留正式用例身份、任务关系与来源，更新字段并追加用例历史。新增用例使用新的正式身份，沿用其 SR 的执行类映射。未选择的字段和用例保持原样。

提交需要登录个人账号并具有当前项目 `case.read`、`run.create` 权限；审核需要 `case.read`、`case.manage`。服务账号令牌不能提交或审核。管理员也可以提交申请，按现有权限审核；本流程不额外限制审核人与提交人必须不同。

## 冲突、事务与容量

- 申请保存不可变的前后数据、正式用例 ID／修订号、个人修订号、提交人和时间。数据快照采用 `schemaVersion: 1` 封装并按 DDT 契约读取。读取列表不包含用例数据正文，展开申请才读取快照。
- 预览后数据有变化，提交会要求刷新差异。审核时使用正式 ID 和修订号条件写；删除后重建同名用例、另一申请已经合入或并发修改都会导致冲突。
- 一个申请的状态、所有正式用例和历史在同一短事务内更新。任意用例冲突则整单回滚，申请保持待审核；退回或撤回后可重新对比提交。不会部分成功或自动覆盖最新数据。
- 请求使用稳定标识，重复提交和重复处理不会重复写入；相反方向的处理竞争由状态条件更新决定。审计日志只包含范围与申请标识，不包含账号数据。
- 每页按游标读取最多 20 个候选或申请。差异只在打开提交弹窗、点击查找、刷新或翻页时计算，不在页面后台循环扫描。一次最多 50 个用例，前后快照合计最多 4 MiB，超出时提示分批提交。
- CaseId 筛选支持完整的 512 字符标识。审核状态和提交范围进入 URL；条件或项目范围变化（包括浏览器前进／后退）时重置分页，避免用旧游标遗漏申请。
- SQLite 使用短 `BEGIN IMMEDIATE` 写事务与有界异步锁重试；快照编码和差异计算在写锁外完成。PostgreSQL 使用事务和条件更新，两种模式共享业务规则。审核合入使正式库后台统计失效并清理浏览器统计缓存。

## 持久化与升级

新增 SQLite `0074_ddt_change_requests.sql`、PostgreSQL `0072_ddt_change_requests.sql`，只增加申请及差异明细表、范围／状态／提交人索引。既有正式和个人数据不搬迁。申请与审核记录在数据库持久化，不依赖 Redis、队列或 Runner；无需对象存储新增资产。

部署前备份数据库，先更新全部 Web 节点。迁移事务失败时回滚该迁移并保留旧业务表，可修复后重新启动；需要退回上一应用版本时保留新增表即可，旧应用不认识审核入口。若恢复数据库，必须使用同一时点的完整备份，不手工删除迁移记录。此次不修改 Runner／Adapter 协议，不新增依赖或在线资源，现有离线资源构建链继续适用。
