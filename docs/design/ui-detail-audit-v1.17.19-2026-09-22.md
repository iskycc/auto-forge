# v1.17.19 UI 细节与操作体验复查

审查日期：2026-09-22。基线：`v1.17.19`，提交 `2aba49657de9c1c1ac64c51434e83e8614b76e0d`。

本轮从平台管理扩展到用例、DDT、任务、执行、分析和质量洞察。本文记录当前实现的 **26 项问题或改进项：3 项 P1、18 项 P2、5 项 P3**。第 1～7 节保留修改前的审查记录，第 8 节记录本次实施与复验；不替代[上一轮管理页报告](platform-management-ui-audit-2026-09-22.md)中的修复记录。

最需要先处理的是分析草稿丢失、DDT 弹窗的草稿保护与键盘行为，以及质量洞察页面的水合错误。视觉上的主要问题则是标题和说明重复、筛选区占屏过多、长文本没有摘要层级、弹窗与操作栏缺少统一规则。单纯继续加圆角或阴影，不能解决这些问题。

## 2. 优先处理的可用性问题

### DETAIL-01 · P1 · 分析弹窗关闭后直接丢失未提交内容

**实测。**在一个未完成的分析中选择“代码问题已提单”，填写问题说明和问题单号，再点击右上角关闭。弹窗直接消失，没有放弃确认；重新打开同一个用例并选择该类别，两个字段均为空。

- [关闭前：已有问题说明与单号](ui-detail-audit-2026-09-22/analysis-unsaved-before-1024.png)
- [重新打开：草稿已丢失](ui-detail-audit-2026-09-22/analysis-unsaved-after-1024.png)
- 代码位置：[CompleteAnalysisDialog](../../apps/web/src/components/failure-analysis-workspace.tsx)。表单使用组件内部 state；背景遮罩、关闭按钮及取消直接调用 `onClose`，没有统一的脏状态关闭入口。
- 影响：填写分析本身耗时较长，误点关闭会导致返工；图片草稿、继承后继续修改、提交中关闭也需要纳入后续修复检查。本轮实际复现的是文字与问题单号，不把其他分支写成已验证。
- 建议验收：未修改时直接关闭；修改后关闭、取消及遮罩统一提示“继续编辑 / 放弃修改”；继续编辑保留全部草稿与附件；提交成功后正常关闭；提交中禁止重复提交和意外卸载。单条与批量分析使用同一规则，不改变继承范围。

### DETAIL-02 · P1 · DDT 自建弹窗缺少完整的焦点和草稿保护

**实测 + 代码。**在 1024px、1536px 均复现：点击“新建模板”后焦点仍停在背景页面的按钮；聚焦弹窗最后一个“创建模板”按钮再按 Tab，焦点离开弹窗；Escape 不关闭。填写 `srNum` 与模板名称后点击关闭，不提示放弃，重新打开名称为空。

- [实际模板弹窗](ui-detail-audit-2026-09-22/ddt-template-keyboard-1024.png)。焦点与草稿结论来自 Playwright 操作记录，不能仅凭这张静态图推断。
- 代码位置：[TemplateDialog 与局部 Dialog](../../apps/web/src/components/ddt-management-workspace.tsx)。局部 Dialog 只有 `role="dialog"` / `aria-modal`，没有焦点迁入、Tab 循环、Escape 处理和脏状态保护。
- 建议复用或统一到 [ActionDialog](../../apps/web/src/components/action-dialog.tsx) 的交互约定，而不是只复制视觉样式。导入冲突等嵌套弹窗需要单独检查顶层焦点和返回位置。
- 建议验收：打开后焦点进入弹窗；Tab / Shift+Tab 不进入背景；关闭后回到触发按钮；Escape 走同一个草稿保护入口；保存期间关闭有明确规则。
- 边界：DDT 用例的行内编辑已有离开保护，不能据此声称所有 DDT 编辑都没有保护。模板之外的复用弹窗还需逐项回归。

### DETAIL-03 · P1 · 质量洞察页面稳定出现 React 水合错误

**实测，根因未定位。**广泛遍历时发现一次 `Minified React error #418`，定向检查定位到 `/insights`；使用相同生产构建和浏览器会话连续三次重新访问，三次均触发该错误。页面最终仍可显示图表，本轮没有证据表明统计数据因此错误或所有操作失效。

- 入口：[质量洞察页面](../../apps/web/src/app/insights/page.tsx)。本轮不将其归因于某个组件，也不猜测是时间、缓存还是 HTML 嵌套导致。
- 下一步应在开发构建获取完整差异栈，比较服务端 HTML 与首次客户端渲染，按证据修复；不得用关闭水合警告来掩盖。
- 建议验收：有数据、无数据、后台快照就绪前后、不同筛选、详情弹窗及重新进入页面均无水合错误；保留后台快照取数模式。

## 6. 建议实施顺序与回归标准

### 第一批：防止输入丢失与修复实际运行问题

处理 DETAIL-01～03，并补上 DETAIL-04 的缺失样式。先编写稳定复现测试，再实现共享的关闭与焦点规则；质量洞察先取得明确根因。不要把整站重排与这批修复放进同一个巨大变更。

### 第二批：高频业务页面的密度与操作位置

优先处理任务详情、DDT 用例/检索、分析表单、执行记录，再处理普通用例页与图表长文本。布局验收除了无重叠、无横向溢出，还应检查：

- 最小桌面首屏能否看见实际列表内容、当前结果或主要输入；不能只剩标题和提示。
- 1536px 下是否合理利用空间，避免一味窄列和多层卡片；2560px 下主要数据仍有清晰阅读顺序。
- 长名称、长类路径、长 URL、无空格字段、空数据、有历史数据和批量选择是否都保持稳定。
- 展开、关闭详情后搜索条件、页码、选择和滚动位置是否保留。
- 高级检索仍为显式提交，并集、仅 Value 匹配、底部分页和弹窗查看均不退化。

### 第三批：统一平台管理的组件规则

处理权限选择密度、固定弹窗操作区、SR 配置引导、保留策略对照、空态与术语。统一组件不等于统一成一样宽的大弹窗：简单表单、权限配置、日志和分析应按信息量选择尺寸，但共享焦点、草稿、加载、错误与关闭行为。

所有实施批次都需保留：Lite/Full 共享业务规则、项目/版本/阶段权限边界、后台快照统计、浏览器缓存、有界查询、用例树按需加载及执行优先级。不能为了前端“更即时”引入输入即写库、全量枚举目录或页面内实时汇总。

另有一项文档一致性工作：[前端设计文档](frontend-design.md)仍含 768px / 手机端布局表述，与根 `AGENTS.md` 当前“仅支持不小于 1024px 桌面”约束不一致。后续应同步文档，本轮没有把手机端纳入验收要求。
